Redis

概念

nosql

  • 泛指非关系型的数据库 ，Not Only SQL
  • nosql的特点
    • 易扩展：去掉关系数据库的关系型特性。数据之间无关系，这样就非常容易扩展。无形之间，在架构的层面上带来了可扩展的能力
    • 大数据量，高性能：具有非常高的读写性能，尤其在大数据量下，同样表现优秀。这得益于它的无关系性，数据库的结构简单
    • 灵活的数据类型：NoSQL无须事先为要存储的数据建立字段，随时可以存储自定义的数据格式。而在关系数据库里，增删字段是一件非常麻烦的事情。如果是非常大数据量的表，增加字段简直就是一个噩梦
    • 高可用：NoSQL在不太影响性能的情况，就可以方便地实现高可用的架构。比如Cassandra、HBase模型，通过复制模型也能实现高可用

Redis

  • 内存中的数据结构存储系统，它可以用作数据库、缓存和消息中间件 ，支持多种类型的数据结构，如 字符串（strings）， 散列（hashes）， 列表（lists）， 集合（sets）， 有序集合（sorted sets） 与范围查询， bitmaps， hyperloglogs 和 地理空间（geospatial） 索引半径查询 ，Redis 内置了 复制（replication），LUA脚本（Lua scripting）， LRU驱动事件（LRU eviction），事务（transactions） 和不同级别的 磁盘持久化（persistence）， 并通过 Redis哨兵（Sentinel）和自动 分区（Cluster）提供高可用性（参考自redis中文官网）

默认有16个数据库 0-15,可以通过 select [db]切换 例: select 10

应用场景

  • 热点信息加速查询 例热点商品
  • 即时信息查询 例排行榜信息,公交到站信息
  • 时效性信息控制 例验证码
  • 分布式数据共享

数据类型

string（简单的KV形式存储）

  • 可自增长
  • 应用场景:播放次数等自增长

hash（K，HashKey，V形式）

  • Hash 便于表示 实例
  • 同一个键 不同的属性来存储数据
  • 拓展:增长传负值可自减
  • 注意:hash value只能存字符串,hgetall可以获取所有属性,如果内部属性过多可能会导致效率低下
  • 应用场景:商城商品的数量问题

list（K，List形式）

  • 底层数据结构：双向链表 特点:有序
  • 扩展:可在指定时间内获取或获取并移除数据
  • 注意:具有索引的概念,但操作数据以队列或栈的形式操作 获取全部数据结束索引为-1
  • 应用场景:可记录多台服务器不同时间点的日志信息, 用户操作信息，可实现生产者，消费者模型
  • 堆,栈,阻塞队列（可以通过RPOPLPUSH 和 BRPOPLPUSH ， BRPOP 和 BLPOP 命令进行阻塞式访问，redis还会为所有阻塞的消费者以先后顺序排队 ）

set

  • 和hash结构类似,在hashKey的位置用于存储数据,value不放数据
  • 扩展:可用于求交集,并集,差集，获取随机元素 等
  • 注意:数据无法重复
  • 应用场景:共同关注

geospatial

  • 时间复杂度：每一个元素添加是O(log(N)) ，N是zset的元素数量

  • 用于存储地理位置,底层实现是zset,官方没有提供删除的命令,可以通过zset命令进行删除

    zrem key value

hyperloglog

  • 概念:基数(一个集合内不重复的元素个数),个人理解可以参照布隆过滤器
  • 优点:比较set保存所有的数据占用的空间小很多
  • 缺点:可能会出现误差,概率大概0.86%

bitmaps

  • bitmaps不是实际的数据类型，而是在字符串类型上定义的一组面向位的操作，由于字符串是二进制安全blob，其最大长度为512MB，因此适合设置为2^32个不同的位

  • 位存储,只存储0 1，在存储时极大地节省了空间，例如，在用增量用户id表示不同用户的系统中，仅使用512MB内存就可以记住40亿用户的一位信息（例如，知道用户是否想要接收时事通讯）

    • BITOP在不同的字符串之间执行逐位操作

    • BITCOUNT执行填充计数，报告设置为1的位数

    • BITPOS查找指定值为0或1的第一位

    • BITPOS和BITCOUNT都可以在字符串的字节范围内运行，而不是在整个字符串长度上运行，BITCOUNT调用的一个简单示例：

  • 应用场景:存储用户是否登录(存储1),是否活跃等,主要是两个状态的都可以使用

事务

  • 概念

    • 开启事务后,所有的操作都会进入队列,直到执行事务再按照入队列的顺序执行
    • 取消事务后队列中的操作都不执行

  • 命令

    • multi

      • 开启事务

    • exec

      • 执行事务

    • discard

      • 取消事务

  • 事务出现异常

    • 编译时异常(命令出错等)

      • 所有的事务都不会执行

    • 运行时异常(出现语法错误)

      • 只有出异常的语句不执行,错误命令抛出异常

数据删除策略

  • 概念

    • 如果redis保存的数据过多会导致性能下降,或内存溢出等情况,就需要删除数据保证新数据的写入

  • 定时删除

    • 创建定时器,当key有设置过期时间且已过期,定时对过期的键执行删除操作

    • 优点

      • 节约内存,定时就删,释放不必要的内存

    • 缺点

      • CPU压力较大,要维护一个定时器,影响redis性能

    • 总结：时间换空间

  • 惰性删除

    • 在键过期时不立即删除,当再次访问这个键的时候才进行删除

    • 优点

      • 节约CPU性能

    • 缺点

      • 占用内存,可能存在大量无效的占用内存数据

    • 总结：空间换时间

  • 定期删除

    • 前提

      • redis中每个db都有对应的expires过期字典,保存了所有键的过期时间

    • 概念

      • 对某个数据库中的过期字典进行随机抽取X个key检测是否过期

        • 过期删除key,如果一次抽查中删除的key的数量超过了抽查总数的25%,则再次抽查当前库中的过期字典进行删除
        • 如果没有超过25%,则抽查下一个数据库的过期字典,数据库0-15轮询
        • 抽查的数量为ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP属性值

    • 总结

      • 定期删除就是周期性轮询redis库中的时效性数据，采用随机抽取的策略，利用过期数据占比的方式控制删除频度
      • 周期性抽查存储空间（随机抽查，重点抽查）

    • 特点

      • CPU性能占用设置有峰值，检测频度可自定义设置
      • 内存压力不是很大，长期占用内存的冷数据会被持续清理

  • 总结

    • 定时删除
      • 节约空间,无占用,,不分时段占用CPU,拿时间换空间
    • 惰性删除
      • 内存占用严重,延迟执行,CPU利用率高,拿空间换时间
    • 定期删除
      • 内存定期随机清理,每秒花费固定CPU资源维护内存随机抽查,重点抽查

数据淘汰策略

  • 概念

    • 即redis容量不足以保存新数据的存储

  • 检测易失数据(设置了过期时间的数据)

    • volatile-lru：挑选最近最少使用的数据淘汰
    • volatile-lfu：挑选最近使用次数最少的数据淘汰
    • volatile-ttl：挑选将要过期的数据淘汰
    • volatile-random：任意选择数据淘汰

  • 检测全库数据(全部数据)

    • allkeys-lru：挑选最近最少使用的数据淘汰
    • allkeLyRs-lfu：：挑选最近使用次数最少的数据淘汰
    • allkeys-random：任意选择数据淘汰，相当于随机

  • 放弃数据驱逐

    • no-enviction（驱逐）：禁止驱逐数据(redis4.0中默认策略)，会引发OOM(Out Of Memory)

  • 配置方法

    • maxmemory-policy volatile-lru

集群方案

主从复制

  • 将redis分为主节点和从节点,一个主节点多个从节点,利用主节点操作写操作,从节点操作读操作,主节点会同步数据到从节点,从节点不会同步数据到主节点

  • 一个master可以拥有多个slave，一个slave只对应一个master

  • 弊端:主节点挂了无法保证写操作

  • 作用

    • 读写分离：master写、slave读，提高服务器的读写负载能力
    • 负载均衡：基于主从结构，配合读写分离，由slave分担master负载，并根据需求的变化，改变slave的数 量，通过多个从节点分担数据读取负载，大大提高Redis服务器并发量与数据吞吐量
    • 故障恢复：当master出现问题时，由slave提供服务，实现快速的故障恢复
    • 数据冗余：实现数据热备份，是持久化之外的一种数据冗余方式
    • 高可用基石：基于主从复制，构建哨兵模式与集群，实现Redis的高可用方案

  • 配置方法

    • 命令配置

      • 只需要配置从服务即可
      • SLAVEOF 主服务器ip 端口

    • 配置文件

      • replicaof 主机ip 端口

      • 如果有主机密码

        • masterauth 密码

哨兵sentinel

redis 2.4后

  • 使用一个哨兵进程监控主节点和从节点,如果主节点宕机后,自动将其的一个从节点转为主节点,继续工作

  • 解决了主节点出现的单点问题,出现哨兵单点 解决:创建多个哨兵进行监控

  • 选举处理主机宕机后处理故障的哨兵算法

    • Raft算法

      • 将时间看为任意个不同长度的任期,每个任期开始时进行选举,每个哨兵都会试图成为处理故障的主哨兵,如果一个候选哨兵成为了主哨兵,那么这个哨兵在接下来的任期剩余时间内都是主哨兵
      • 如果选举没有投出主哨兵,就会开始另一个任期,并立刻开始下一次的选举,保证了每个任期最多有一个主领导人

  • 选举主机宕机后切换为主机的算法

    • 选择健康状态从节点,排除5秒钟没有心跳的、排除主节点失联超过10 * down-after-millisecends
    • 选择配置中优先级最高的
    • 选择复制数据偏移量最大的从机
    • 如果还没有选出来，则按照从机ID排序，获取运行ID最小的从节点

内置集群cluster

redis 3.0后

  • 概念:去中心化,将数据分散保存在不同的节点上,所有节点互通,如果访问的节点没有需要的数据,会找到有需要数据的节点访问(数据分片)
  • 数据分配方式:采用哈希槽的方式分配,默认有16384个哈希槽,将这些哈希槽平均分成节点个数的份数,这时每个节点有对应的哈希槽
    数据保存时会根据键值计算对应的哈希槽值,判断是保存到哪个节点中
  • 计算哈希槽算法: CRC16 (“key”) % 16384
  • cluster的主从模式:在多个节点后还有一个从节点,从节点会实时同步主节点数据,在主节点宕机后,从节点自动替换为主节点

缓存相关问题

缓存穿透

  • 查询数据库内不存在的数据,而不保存到缓存中,跳过了缓存频繁的访问数据库,达到跳过了缓存的目的
  • 解决:将查询到的不存在的数据也保存到缓存中,并设置过期时间

缓存雪崩

  • 多个热门的缓存数据在同一个时间点失效过期,过期后同时进行查询,会造成数据库的周期性压力
  • 解决:设置比较热点的数据失效时间长一些,冷门数据失效时间短一些，搭建集群实现高可用

缓存击穿

  • 一个特别热点的缓存数据在失效过期的同时,大量的访问会直接访问到数据库上,如双十一热点访问,导致一个请求多次频繁访问数据库
  • 解决:设置特别热点的数据永不过期

Redis常见数据丢失情况分析及解决

情况分析

  • 异步复制导致的数据丢失

    • 因为master同步到slave的数据是异步的，所以可能存在部分数据还没有同步到slave，master就宕机了，此时这部分数据就丢失了

  • 脑裂导致的数据丢失

    • 当master出现网络波动，与其他slave、sentinel失去了连接，但是master还在运行着。此时sentinel发送ping后没有收到pong响应就会认为master宕机了，会开始选举把slave提升为新的master，这个时候集群中就会出现两个master，也就是所谓的脑裂
    • 此时虽然产生了新的master节点，但是客户端可能还没来得及切换到新的master，会继续向旧的master写入数据
    • 当网络恢复正常时，旧的master会变成新的master的从节点，自己的数据会清空，重新从新的master上复制数据

解决方案

  • Redis提供了 min-slaves-to-write 和 min-slaves-max-lag配置来降低数据丢失的可能性
    • min-slaves-to-write 表示连接到master的最少slave数量
    • min-slaves-max-lag 表示slave连接到master的最大延迟时间
    • 如果master宕机后slave数据复制和同步的延迟超过了配置的时间master就会拒绝写请求,保证数据的最小丢失
    • 如果一个master出现了脑裂，跟其他slave丢了连接,原先的master节点接收到客户端的写入请求会拒绝，就可以减少数据同步之后的数据丢失

Redis并不能保证数据的强一致性,官方文档原话

  • Redis 并不能保证数据的强一致性. 这意味这在实际中集群在特定的条件下可能会丢失写操作.
