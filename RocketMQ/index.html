RocketMQ

官方中文文档
https://github.com/apache/rocketmq/blob/master/docs/cn

概述

RocketMQ 是阿里巴巴2016年MQ中间件，使用 Java 语言开发，在阿里内部，RocketMQ 承接了例如“双11”等高并发场景的消息流转，能够处理万亿级别的消息

为什么要用MQ

消息队列是一种“先进先出”的数据结构 ，一般作为高并发系统的核心组件之一，能够帮助业务系统解构提升开发效率和系统稳定性

优点

  • 应用解耦
  • 快速应用变更
  • 流量销峰

缺点

  • 宕机问题

    • 解决方案:集群

  • 复杂性提高，

  • 异步机制

    • 消息顺序无法保证
    • 消息丢失
    • 消息一致性无法保证
    • 消息重复消费

消息队列中间件

基本概念

  • Producer生成者

    • 消息发送方

  • Consumer消费者

    • 消息处理方

  • topic主题

    • 每个消息的分类,消息的集合

  • Broker Server代理服务器

    • 消息中转角色，负责存储消息、转发消息

  • Name Server名字服务

    • 名称服务充当路由消息的提供者

基本使用

发送

  • 发送步骤

    • 生产者发送消息到nameServer,启动服务,发送消息对象,关闭连接

  • 消息类别

    • 同步消息

      • 即时性强,必须有回应

    • 异步消息

      • 即时性较弱,需要有回应 例:订单下单,未支付状态
      • 调用方法后 操作回调对象

    • 单向消息

      • 不需要有回应,例:日志类消息

  • 延时消息

    • 设置消息的延迟级别

  • 批量消息

    • 将消息对象存到集合中发送

      • 消息总长度不超过4M,消息总长度包含4个信息,topic,body,消息追加的属性,日志(固定20字节)

  • 过滤

    • tag过滤

      • 发送时设置对应的tag

    • sql过滤

      • 默认不支持,修改配置文件
      • 在发送时添加属性

接收

  • 消费模式

    • Clustering负载均衡模式

      • 每个消费者收到的消息数量都是相同的

    • Broadcasting广播模式

      • 每个消费者收到的消息都是总的消息数

    • 多个生产者产生的消息可以被同一个消费者消费

  • 接收步骤

    • 类似生产者,创建接收消息方,设定命名服务器地址,对应的topic和sub标签,需要再开启监听用于接收消息,启动接收消息服务

  • 过滤消息

    • tag过滤

      • 获取时按tag类型获取

    • sql过滤

      • 接收时按属性过滤

消息顺序

  • 出现顺序错乱原因

    • 在每个topic中的tag中还有多个消息队列
    • 这多个消息队列接收消息的顺序是随机的
    • 消息错乱的情况就出现了

  • 如何保证消息队列的顺序

    • 将同一个操作的消息,按顺序进入同一个队列
    • 将多个消息保存到一个集合中,遍历集合,调用send三参数方法，指定要发送的队列
    • 传入参数第二参数为消息队列选择器,匿名内部类重写方法,该方法返回哪个队列则将消息保存到哪个消息队列
    • 根据消息通过算法将消息的id转化为消息队列集合中的索引值,返回计算出索引值位置的索引
    • 算法:通过消息id的 hashcode值 % 消息队列集合长度 ,得出的结果为消息队列的索引

事务消息

  • 三种状态

    • 提交事务，它允许消费者消费此消息
    • 回滚事务，它代表该消息将被删除，不允许被消费
    • unknown中间状态，它代表需要检查消息队列来确定状态

  • 步骤

    • 更改生成者为事务消息生产者

    • 更改事务消息发送方式

    • 添加事务监听器

      • 匿名内部类重写方法

      • execue方法为正常事务过程

      • check方法为补偿机制过程

集群

主从服务器区别

  • 主服务器负责写操作,从服务器负责读操作

集群概念

  • 多个broker提供服务

  • 多个master多个slave

    • master到slave的消息同步方式

      • 同步:较异步方式性能略低,消息无延迟
      • 异步:较同步方式性能更高,消息有延迟,可能会造成消息少量丢失

集群特征

  • NameServer是一个几乎无状态节点，可集群部署，节点之间无任何信息同步
  • Broker部署相对复杂，Broker分为Master与Slave，一个Master可以对应多个Slave，但是一个Slave只能对应一个
  • Master，Master与Slave的对应关系通过指定相同的BrokerName，不同的BrokerId来定义，BrokerId为0表示Master，非0表示Slave。Master也可以部署多个。每个Broker与NameServer集群中的所有节点建立长连接，定时注册Topic信息到所有NameServer
  • Producer与NameServer集群中的其中一个节点（随机选择）建立长连接，定期从NameServer取Topic路由信息，并向提供Topic服务的Master建立长连接，且定时向Master发送心跳。Producer完全无状态，可集群部署
  • Consumer与NameServer集群中的其中一个节点（随机选择）建立长连接，定期从NameServer取Topic路由信息，并向提供Topic服务的Master、Slave建立长连接，且定时向Master、Slave发送心跳。Consumer既可以从Master订阅消息，也可以从Slave订阅消息，订阅规则由Broker配置决定

总结

  • nameserver有 多个
  • master 多个,每个master 都有多个 slave
  • master 的 brokerid =0 , slave 的 brokerid 非0
  • 多个 master 和多个slave 如果 brokername 相同则 为一组
  • master 和slave 会将自己注册到每一台 nameserver 上

特性

消息持久化

  • 持久化的操作由broker将数据保存到文件系统中,跳过了经过数据库的步骤,引入消息存储

消息存储

  • 零拷贝

    • linux中发送数据会将数据进行多次转换
    • 数据传输由传统的4次复制简化成3次复制,减少1次复制过程，加快了速度

消息存储结构

  • 消费逻辑队列

    • 消息消费顺序等

  • 索引

    • 创建索引时间,key索引等

  • 在消息存储区域外,再开辟了逻辑队列和索引分别存储消息数据,在查找时可以根据索引查找对应消息数据,不需遍历消息存储区域内所有消息队列

刷盘机制

  • 同步

    • 安全性高,效率低,速度慢
    • 生产者发送消息给broker,broker将生产者先挂起后,将消息数据保存完成后才将生产者唤醒

  • 异步

    • 安全性低,效率高,速度快
    • 生产者发送消息后,broker不挂起,生产者可继续发送消息,broker将消息保存到一定量之后再进行持久化

高可用

  • nameserver集群,每个broker都对每个nameserver进行注册
  • 消息服务器为主从架构,主服务宕机,从服务只提供消费服务
  • 将相同topic绑定到多个group,保证主服务宕机后,其他主服务的正常接收
  • 读写分离 当master繁忙时候，自动切换由slave承担数据读取的工作

主从复制

####Broker 的角色

  • ASYNC_MASTER 异步复制Master

  • SYNC_MASTER 同步双写Master

  • SLAVE

  • 同步

    • master接到消息后，先复制到slave，然后反馈给生产者写操作成功
    • 优点：数据安全，不丢数据，出现故障容易恢复
    • 缺点：影响数据吞吐量，整体性能低

  • 异步

    • master接到消息后，立即返回给生产者写操作成功，当消息达到一定量后再异步复制到slave
    • 优点：数据吞吐量大，操作延迟低，性能高
    • 缺点：数据不安全，会出现数据丢失的现象，一旦master出现故障，从上次数据同步到故障时间的数据将丢失

负载均衡

  • 生产者

    • 轮询机制

  • 消费者

    • 平均分配

      • 将消息队列总数和消费者总数除了之后平均分配

    • 循环平均分配

      • 将消息队列总数和消费者总数除了之后每个topic中获取对应的数量进行分配

消息重试机制

  • 顺序消息

    • 当消费者消费完成之后,没有进行回应,broker就会进行重试,间隔1s一次
    • 注意:如果一直重试失败,会出现消息阻塞情况,需进行监控

  • 无序消息

    • 只适用于负载均衡消息消费,MQ设定了合理的消息重试间隔时长,默认进行十六次重试

    • 重试十六次过后如果还未被消费,则将该消息标记为死信消息,保存到死信队列中

      • 死信消息

        • 死信队列特征

          • 死信队列归属某一个组（Gourp Id），而不归属Topic，也不归属消费者
          • 一个死信队列中可以包含同一个组下的多个Topic中的死信消息
          • 死信队列不会进行默认初始化，当第一个死信出现后，此队列首次初始化

        • 死信队列消息特征

          • 不会被再次重复消费
          • 死信队列中的消息有效期为3天，达到时限后将被清除

        • 死信处理

          • 在监控平台中，通过查找死信，获取死信的messageId，然后通过id对死信进行精准消费

消息重复问题

  • 原因:网络问题

  • 保证一样的消息只能被消费一次

  • 解决

    • 幂等

      • 保证同一条消息,无论消费次数多少,消费结果都一致

    • 使用唯一的一个id作为消息的key

    • 在消费时,如果已经消费过,就不再进行消费

主流MQ对比

  • ActiveMQ：java语言实现，万级数据吞吐量，处理速度ms级，主从架构，成熟度高
  • RabbitMQ ：erlang语言实现，万级数据吞吐量，处理速度us级，主从架构
  • RocketMQ ：java语言实现，十万级数据吞吐量，处理速度ms级，分布式架构，功能强大，扩展性强
  • kafka ：scala语言实现，十万级数据吞吐量，处理速度ms级，分布式架构，功能较少，应用于大数据较多
